# 模块化单体优先，微服务按门槛演进

首期以可部署的模块化单体作为基线，内部保留 IAM、Content、Learning 三个业务模块和清晰的模块边界，Gateway 等分布式基础设施后置。模块接口、数据所有权、事务边界和进程内事件从第一天按微服务纪律维护。服务抽取只在出现生产压力（独立发布、独立扩缩容、故障隔离、团队协作、实际维护压力）或学习门槛（第一阶段退出条件达成后的拆分演练）时触发，第一次拆分对象为 Content。

## Status

accepted

## Consequences

- 模块是代码和业务接口边界，服务是部署边界，两者分开讨论。
- 首期不使用 Gateway、注册中心、配置中心、消息队列、分布式事务和链路追踪。
- 跨模块禁止直接查表和跨 schema join，数据访问一律走模块接口。
- 事务边界在模块内，跨模块写使用进程内事件，幂等、重试、Outbox 在服务抽取阶段引入。
- 技术栈选择以主流性和演进能力为准，详见 docs/research/单体阶段技术栈基线调研.md。

## Amendment（2026-08-05）

触发条件具体化：首期三模块验收通过后，出现以下任一情况时评估 Content 抽取：报名或资格授予流程出现跨模块事务性协调需求、模块边界在代码中频繁被越、进入微服务拆分演练的学习门槛。其余后置能力（考试、交易支付、企业培训、AI 顾问、Kubernetes）在对应需求出现时解封各自决策票据，触发条件清单见 AGENTS.md「阶段门槛与触发检查」。
