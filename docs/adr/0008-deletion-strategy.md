# 删除策略：默认物理删除，生命周期交给状态字段，不做全局软删除

数据行的删除用三种手段分工，不引入全局 `deleted` 列。纯叶子数据物理删除；被其他表引用、或业务上"必须从当前视图消失"的实体用状态字段停用；只有真实出现"必须保留历史且要从业务视图隐藏"的实体才按表单独评估软删除或归档。

## Status

accepted

## Considered Options

- **全局软删除（全表接入 `@TableLogic`）**：MyBatis-Plus 教程的主流画风，加一列 `deleted` 加一个注解，所有查询自动过滤已删除行，宣称防误删、可恢复。问题在于：`deleted` 只有 0/1 两态，表达不了停用、封禁、注销、取消这些更丰富的生命周期，和现有状态字段并存成两套语义；唯一约束会撞车，`iam.user` 的 username、phone 被软删除后仍占住唯一键，新注册同号会被 `Duplicate entry` 挡住，必须改造唯一索引才能绕开；每次查询、联表、计数都背着隐式的 `deleted=0` 条件，数据行长期堆积后索引膨胀，还要额外写清理任务，与"保留数据"的初衷自相矛盾。
- **状态字段承担生命周期**：行不删，`status`、`enabled` 这类列表达当前是否可用。订单从下单到取消到退款走状态机，账号停用、字典下架都用状态表达。语义丰富、查询直白、被引用的行不会成为孤儿，是企业项目里真正的主流。
- **物理删除**：`DELETE` 直接抹掉行。适合 token、验证码、临时文件、垃圾数据等叶子数据，被其他表引用或有保留价值的行不能用。

## Decision

采用状态字段承担生命周期、叶子数据物理删除的组合，不做全局软删除。`BaseEntity` 不引入 `deleted` 列。具体分工：

- 被其他表引用、或业务上必须从当前视图消失的实体，用状态字段表达（`UserStatus.ACTIVE/INACTIVE`、`dict_item.enabled` 等），行不删除。
- 无引用、无保留价值的叶子数据物理删除。
- 某个实体出现"必须保留历史行且从业务视图隐藏"的真实需求时，按表单独评估软删除或归档，不进 `BaseEntity`，并同步处理唯一约束交互。

## Consequences

- 已有状态字段继续承担全部生命周期语义，不新增 `deleted` 列，查询和索引保持直白。
- 用户账号这类被未来 Content / Learning 模块引用的行，用停用表达"删除"，行保留、引用不断。
- 重新评估触发条件：出现必须保留历史且需隐藏可恢复的实体（例如用户删除自建课程但学习记录需留存），或个保法对特定数据的删除义务与本策略冲突。
