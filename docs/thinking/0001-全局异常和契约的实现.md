# 全局异常和契约的实现是怎么构思的

> 功能：统一响应 + 全局异常 + 参数校验格式化（首期-02 API 契约基础的一部分）
> 关联票据：[首期-02 #16](https://github.com/L1248708823/learning-certification-platform/issues/16)
> 对应代码：backend/src/main/java/com/learningplatform/common/ 下的 api、exception、web 三个包
> 状态：第二稿，等你校准

这篇记的不是代码，是接到这个功能时脑子里怎么想的那条线。代码长什么样、为什么这么写，注释里有，我不重复。这里讲四件事：怎么发现有哪些方案可选、方案的写法从哪抄、怎么走出一条主线、怎么测。每篇末尾抽一句能复用的方法。

## 这团麻的线头在哪

接到"统一响应和全局异常"这个功能，我没有先去翻 Spring 有没有现成组件，而是先问一个问题：前端到底需要什么。

前端跟后端打交道，心里只有两件事。成功的时候，它要知道数据放在响应的哪个位置，直接取就行。失败的时候，它要知道错在哪个类型、能不能把错误展示给用户。前端最怕的是每个接口返回的形状都不一样，同一个错误在 A 接口是 `{code:1}`，在 B 接口是 `{message:"xxx"}`，那前端就得为每个接口写一套解析逻辑。这是前后端分开之后最容易烂的地方。

所以线头从这里抽：先定"成功的响应长什么样"，也就是 `ApiResponse{code, message, data}`。ApiResponse 是统一响应体，所有接口都返回这个壳子。定了这个形状，错误只是这个形状的一种填充方式。

为什么先定成功？因为成功是所有接口共用的，它把响应的形状钉死，错误处理、参数校验都是在同一个壳子里换内容。先有一个稳定的壳，再往里面塞各种失败的情况，心里才踏实。

这一步的思维是倒推：从使用者的出口往回走，不从技术组件往前走。写前端的时候其实一直在这么干，换到后端，第一反应反而变成了"该用哪个框架组件"，这个错位就是知识的诅咒在作怪。

## 选项空间是怎么冒出来的

这一段最想讲清楚，因为"我一开始怎么知道有全局异常捕获这种东西"是新手最大的坎。

先捅破一层窗户纸。在 Spring 生态里，"把异常统一转成 HTTP 响应"是被无数项目反复解决过的问题，所以它有一个标准答案，写在官方文档里。不需要从零发明，需要的是知道去哪把它找出来。发现路径有三条，是真实的。

第一条是 Spring 官方文档。搜 "Spring MVC handling exceptions"，官方文档有一整章专门讲这个，把 `@ExceptionHandler`、`@ControllerAdvice` 这些方案列全了，还解释了全局处理和每个 controller 单独处理的取舍。`@ControllerAdvice` 是一个标在类上的注解，`@RestControllerAdvice` 是它在 REST 接口下的变体，标了它之后，类里的异常处理方法会对整个应用的所有 controller 生效，等于一个全局错误出口。知道有 `@RestControllerAdvice`，来源就是官方文档这一章。新手不用背注解，关键在知道去哪查，官方文档的目录比搜索引擎的零散博客可靠得多。

第二条是看真实项目。任何上过线的 Spring Boot 仓库，几乎都长着同一个样子：一个 `@RestControllerAdvice` 的类、一个统一响应类、一个业务异常类。模式见多了，就从知识变成常识。专家脑子里方案清单自动浮现，是因为他见了一百次，新手才见第一次，差别在见没见过，不在聪明不聪明。

第三条是前端经验的迁移。前端写过 axios 拦截器统一处理响应，或者全局的错误处理，这个心智模型可以原封不动平移到后端。前端的拦截器就是后端的全局异常处理器，做的事一模一样：不让错误处理散落在每个调用点，集中到一个出口。这个能力早就有了，换了一门语言，一时认不出来而已。

候选清单浮出来之后长这样：手动在每个接口 try-catch，散落而且重复；`ResponseStatusException`，只能定 HTTP 状态码，定不了业务错误码、塞不进统一 body；`@ExceptionHandler` 放在单个 controller 里，只管自己这一个；`@RestControllerAdvice`，全局集中。前几个都解决不了"横切"这个本质问题，只有最后一个是为横切而生的，所以不用纠结。

这里还有一层新手容易漏掉的：知道有哪些方案，还得知道方案里的代码怎么写。`@ExceptionHandler` 括号里放异常类型，方法入参放异常本身，返回 `ResponseEntity` 控制状态码和 body，这些写法不是想出来的，是 Spring 框架定好的约定，官方文档的异常处理章节有现成的示例代码。我写 `GlobalExceptionHandler` 就是照着官方示例，把 `BusinessException`、`ApiResponse` 换成我自己的业务类型。新手写这类代码的正路是抄官方模板再改成自己的，不是凭空发明，抄模板加解释是正常且正确的路径。

## 主线上怎么走

方向定了以后，代码的组织顺序是顺着依赖关系一层层往上搭的，这个顺序本身有讲究。

先有 `ApiResponse`，响应的形状，整个功能的地基。用 Java 21 的 record 写，record 是 Java 16 起的语言特性，定义不可变数据载体，自动生成构造器、getter、equals、hashCode，不用引 Lombok 这个额外库。

再往上 `ErrorCode` 枚举，把业务错误码和 HTTP 状态码绑在一起。为什么绑？因为"这个错误该回 400 还是 404"是一个语义判断，这种判断应该集中在一个地方定义，散在 handler 里就会重复，改一处漏一处。

再往上 `BusinessException`，业务代码抛异常时带上错误码。业务层表达"这里不合法"只需要 `throw new BusinessException(ErrorCode.STATE_CONFLICT)`，它不需要知道响应长什么样，不用自己拼。

最上面才是 `GlobalExceptionHandler`，类上标 `@RestControllerAdvice`，按异常类型分方法接住，把异常翻译成前面的壳。

为什么这个顺序？因为依赖是单向的：handler 依赖 exception，exception 依赖 errorCode，errorCode 是纯定义，谁都不依赖。从最底层的"数据形状"往上搭，每一层只依赖下面已经确定的东西，这是拆解这类功能比较稳的顺序，不用回头改。

参数校验是主线上的一个附加站。`@Valid` 标在 `@RequestBody` 参数上，Spring 会调用 Bean Validation 这套 Java 官方的校验规范去检查，不通过就抛 `MethodArgumentNotValidException`。handler 接住它，把每个字段的错误转成 `data` 里的明细列表。为什么放 data 不放 message？因为前端要逐字段展示错误，塞在 message 里前端就得解析字符串，很脆，字段一多就崩。

## 岔路与犹豫

写的过程中有两个真实的犹豫，当时不是一下就拍板的。

第一个犹豫：兜底 handler 要不要把异常信息透给前端。开发时透出来其实很方便，一眼能看到错在哪。但生产环境一旦透出去，SQL、堆栈、内部实现细节都可能被用户看到，这是安全风险。最后选了不透，回固定的"系统内部错误"，完整堆栈只记在服务端日志。这里有一条判断准则：给用户的响应只给用户需要的，排查用的东西留在日志里。这个直觉不是查文档查来的，是安全上的常识。

第二个犹豫：这一票的测试要不要上 Testcontainers。规格的测试基线写了持久化相关的测试用 Testcontainers 连真实 MySQL。Testcontainers 是测试时用 Docker 起真实容器的库。但这一票是纯 Web 契约层，一根数据库都不碰。我选择在测试里排除数据源和 Flyway 的自动配置，让测试离线就能跑。这里的教训是：测试成本要跟被测对象匹配，契约层测的是响应形状，为它起一个数据库容器是浪费，等首期-03 碰真库的时候再上 Testcontainers，那才是它该出场的地方。

## 怎么测试

这个功能要验证的是"异常进来、响应出去"的整条链路，所以用集成测试，不用单元测试。单元测试只测 handler 方法本身，测不出 controller 抛异常之后 Spring 怎么把它路由到 handler 这条真实路径。

搭法用 `@SpringBootTest` 加 `@AutoConfigureMockMvc`。`@SpringBootTest` 会启动整个应用上下文，把所有 bean 装配起来。`@AutoConfigureMockMvc` 装配 MockMvc，一个不打真实网络端口、直接调用 controller 层的模拟 HTTP 客户端。测试里用 `mockMvc.perform` 发请求，断言返回的 HTTP 状态码和响应体 JSON。

这一票特意在测试配置里排除了数据源和 Flyway 的自动配置，因为本票不碰数据库。不排除的话，`@SpringBootTest` 启动时会尝试连数据库，测试就依赖服务器隧道，没法离线跑。这是个主动的取舍，等首期-03 需要真库时，测试会换成 Testcontainers 起容器。

测试用例覆盖五个验证点：成功响应的形状、业务异常映射的 HTTP 状态码、参数校验失败的字段明细、请求体格式错误、兜底的安全 message。每个用例对应契约的一个行为，看完测试就知道这个契约保证了几件事。

## 一句话沉淀

接到一个功能，先从前端的出口倒推，它要收到什么形状的成功、什么形状的失败，把横切的东西（异常、响应格式、参数校验）全部收进一个出口；发现候选方案靠官方文档和真实项目，代码写法照官方模板抄再改成自己的；测试用集成测试打整条链路，测试成本跟被测对象匹配。
