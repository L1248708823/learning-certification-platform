# 注册验证码和写库顺序是怎么构思的

> 功能：手机号验证码注册里，核对、写库、消费验证码的顺序
> 关联票据：[首期-03 #17](https://github.com/L1248708823/learning-certification-platform/issues/17)
> 对应代码：`RegistrationService`、`VerificationCodeService`、`VerificationCodeStore`
> 状态：第一稿，等你校准

注释里写了为什么先核对再写库。这篇只补注释没写的那条思维线：我怎么知道这里有坑，方案从哪来。

## 这团麻的线头在哪

注册看起来是一件事：码对了就建用户。真正有两份状态，一份在 Redis（验证码），一份在 MySQL（用户行）。`@Transactional` 只管第二份。线头不是 Spring 注解怎么写，是这两份状态谁先动。

## 选项空间是怎么冒出来的

前端经验里，提交表单失败后验证码还在，用户改个用户名就能再试。这个体感平移过来，就是写库失败时码不能先被删掉。

生产里这叫跨资源没有分布式事务。常见三条路：先消费再写库，写失败就认栽让用户重发短信；先写库再消费，码错了用户已经建出来；拆成核对和消费两步，核对通过再写库，成功才删码。第三条同时保住「码错不能建用户」和「建用户失败码还在」。

Redis 消费用 Lua 把 GET 和 DEL 绑在一起，写法来自 Redis 官方脚本示例，不是自己发明的锁。

## 主线上怎么走

先定存储边界 `VerificationCodeStore`，生产和测试各一个实现。再在 `VerificationCodeService` 上拆 `assertValid` 和 `consume`。最后 `RegistrationService` 按核对、查重、写库、消费往上排。查重放在验码后面，没有有效验证码，接口不会告诉你这个名字注册过没。

## 岔路与犹豫

要不要用事务提交后再消费？更严，单元测试没有 Spring 事务时会额外分叉。首期接受「方法里写库成功立刻消费」，提交失败这种窗口极窄，留给以后再收。

## 怎么测

规则用内存存储加假 Mapper 锁住：写库撞唯一约束，码还能被消费。HTTP 加真 Redis、真 MySQL 的集成测试锁住：用户名冲突后换名字，同一条码还能注册成功。`mvn test` 不跑 `*IT`，集成测试要 Docker，走 `mvn verify`。

## 一句话沉淀

两份状态没有同一把锁时，先问失败以后哪一份必须还在，再决定谁先动。
