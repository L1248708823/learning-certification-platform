# 微服务基础设施与本地运行调研

## 研究范围

为在线教育与职业认证平台确定 Gateway、服务发现、配置管理、认证接入、本地 Docker Compose、服务独立启动、Java 容器镜像和开发环境的首期基线，并记录暂缓引入的基础设施。

访问日期：2026-08-04。

## 结论摘要

首期采用 Spring Cloud Gateway Server WebFlux 作为统一入口，领域服务继续使用 Spring MVC。Gateway 负责路由、路由级认证、Token Relay、跨域和请求追踪；领域服务继续独立校验 Access Token，并负责资源级授权。

首期不依赖独立服务注册中心和配置中心。Docker Compose 服务名用于本地寻址，普通配置使用 Spring Profile 和环境变量。服务注册中心、配置中心和其他平台基础设施保留学习实验与正式引入门槛。

认证采用标准 OAuth 2.0、OpenID Connect 和 JWT 组合。IAM 集成 Spring Authorization Server，React 使用 Authorization Code + PKCE，IAM 使用非对称密钥签发 JWT 并通过 JWKS 发布公钥。服务间调用默认使用 Client Credentials。

本地默认模式只启动数据库、Redis 等基础依赖，应用服务由 IDE 或命令行独立启动；全链路验收模式使用 Docker Compose Profile 启动 Gateway 和全部应用服务。Java 基线为 Java 17 LTS，构建使用 Maven Wrapper，镜像采用多阶段构建和非 root 运行用户。

## 官方事实与来源

### Gateway 实现

Spring Cloud Gateway 官方同时提供 Server WebFlux 和 Server Web MVC。Server WebFlux 建立在 Spring WebFlux 之上，使用异步、响应式运行模型；Server Web MVC 建立在传统 Servlet 模型之上，两者都支持路由、谓词和过滤器。

来源：

- [Spring Cloud Gateway Server WebFlux](https://docs.spring.io/spring-cloud-gateway/reference/spring-cloud-gateway-server-webflux.html)
- [Spring Cloud Gateway Server Web MVC](https://docs.spring.io/spring-cloud-gateway/reference/spring-cloud-gateway-server-webmvc/how-it-works.html)

Gateway 的 TokenRelay 过滤器可以把入站 OAuth2 Access Token 转发给下游服务。Token Relay 解决令牌传递，不能替代下游服务对令牌和资源权限的独立校验。

来源：[Spring Cloud Gateway TokenRelay Filter](https://docs.spring.io/spring-cloud-gateway/reference/spring-cloud-gateway-server-webmvc/filters/tokenrelay.html)

### Resource Server 与令牌校验

Spring Security Resource Server 支持 JWT 本地验证。服务会校验签名、公钥、时间声明和签发者，并把 scope 映射为权限。Opaque Token 模式则要求服务调用授权服务器的 introspection endpoint，适合需要集中撤销判断的场景，同时增加对授权服务器的运行时依赖。

来源：

- [Spring Security Resource Server JWT](https://docs.spring.io/spring-security/reference/7.0/reactive/oauth2/resource-server/jwt.html)
- [Spring Security Resource Server Opaque Token](https://docs.spring.io/spring-security/reference/7.0/reactive/oauth2/resource-server/opaque-token.html)

### Spring Authorization Server

Spring Authorization Server 是构建 OAuth 2.1 和 OpenID Connect 1.0 授权服务器的 Spring 框架。官方实现包含授权、Token、撤销、introspection、授权服务器元数据、JWK Set 和 OIDC 相关端点，并允许将注册客户端、授权记录和用户同意持久化到应用自己的数据存储。

来源：[Spring Authorization Server Overview](https://docs.spring.io/spring-authorization-server/reference/overview.html)

### Java 与构建环境

Spring Boot 要求 Java 17 或更高版本。Spring Boot 3.5 的官方系统要求以 Java 17 为最低版本，并支持到 Java 25。项目选择 Java 17 LTS 可以满足 Spring Boot 基线，并保持与当前开发机环境一致。

来源：

- [Spring Boot System Requirements](https://docs.spring.io/spring-boot/system-requirements.html)
- [Spring Boot 3.5 System Requirements](https://docs.spring.io/spring-boot/3.5/system-requirements.html)

Maven Wrapper 用于让项目通过仓库内的 Wrapper 配置固定 Maven 版本，开发、CI 和 Docker 构建使用同一入口。

来源：[Apache Maven Wrapper](https://maven.apache.org/tools/wrapper/)

## 候选方案比较

### 服务发现

| 方案 | 优点 | 当前代价或限制 | 结论 |
| --- | --- | --- | --- |
| Docker Compose 服务名 | 零额外服务，适合固定单机拓扑 | 不处理动态实例和跨平台寻址 | 首期默认方案 |
| Eureka、Consul、Nacos | 支持注册、发现和部分健康治理 | 增加运行时、配置和故障面 | 学习实验或触发后引入 |
| Kubernetes Service | 使用平台原生服务发现 | 依赖 Kubernetes | 进入 Kubernetes 后优先采用 |

### 配置管理

| 方案 | 适用场景 | 首期结论 |
| --- | --- | --- |
| Spring Profile 加环境变量 | 服务少、环境少、配置变更不频繁 | 默认采用 |
| 独立配置中心 | 多服务多环境共享配置、版本审计、动态刷新和配置漂移明显 | 触发后评估 |
| Kubernetes ConfigMap 和 Secret | 已进入 Kubernetes 的部署环境 | 优先使用平台能力 |

### IAM 与授权服务器

Keycloak 是独立的 IAM 产品，提供用户管理、管理控制台、身份联邦、社交登录、MFA、SSO 和 OAuth2/OIDC 能力。Spring Authorization Server 是嵌入 Spring 应用的协议框架，需要项目自己实现或集成用户管理、登录界面、客户端管理和业务权限模型。

当前领域上下文已经将用户、凭证、会话、Token 和平台角色归入 IAM。为了保持这个边界并学习标准协议，首期使用 Spring Authorization Server；Keycloak 作为后续外部 IAM 对比实验。

来源：

- [Keycloak](https://www.keycloak.org/)
- [Spring Authorization Server Overview](https://docs.spring.io/spring-authorization-server/reference/overview.html)

## 首期基线

### Gateway 与服务启动

- Gateway 使用 Spring Cloud Gateway Server WebFlux。
- 学习者端和后台前端通过 Gateway 访问领域服务。
- 领域服务默认只在内部网络访问，但每个服务仍可在 IDE 或命令行中独立启动。
- Gateway 不是领域服务启动的前置条件，正式验收流程统一经过 Gateway。

### 认证与授权

- IAM 使用 Spring Authorization Server，提供 OAuth 2.0 和 OpenID Connect 标准端点。
- React 使用 Authorization Code + PKCE。
- IAM 使用非对称密钥签发 JWT Access Token，并通过 JWKS 发布公钥。
- Gateway 做路由级认证和 Token Relay；领域服务作为 Resource Server 独立验证 JWT。
- JWT 使用 `iss`、`aud`、`exp`、`scope` 等稳定声明。
- scope 用于接口级权限，领域服务根据本地数据完成课程归属、学习资格等资源级授权。
- 服务间调用默认使用 Client Credentials。只有下游确实需要用户上下文时才传递用户 Access Token。

### 本地运行与配置

- 默认 Compose 模式只启动数据库、Redis 等基础依赖。
- 全链路验收模式使用 Compose Profile 启动 Gateway 和全部应用服务。
- `application.yml` 保存安全通用默认值，`application-local.yml` 保存本地开发配置，环境变量覆盖地址和端口。
- `.env.example` 可以提交，真实 `.env`、密码、私钥和 Token 不提交。
- 服务注册中心和配置中心不进入默认启动链路。

### 构建与运行时

- Java 17 LTS 作为项目基线。
- 使用 Maven Wrapper，开发、CI 和 Docker 构建统一使用 Wrapper。
- Docker 使用多阶段构建，构建阶段使用 JDK，运行阶段使用 Java Runtime。
- 容器基线采用 Eclipse Temurin 17，镜像版本固定，容器使用非 root 用户。
- 当前不使用 Distroless，保留调试能力。

### 最低运行检查

- 每个服务引入 Spring Boot Actuator。
- `liveness` 表示进程是否仍能工作，`readiness` 表示必要依赖是否可用。
- 健康端点只在内部管理端口或内部网络暴露，不通过 Gateway 对外提供。
- 其他 Actuator 端点默认关闭。
- Docker Compose 可读取健康状态，但业务正确性不能依赖固定启动顺序。

## 暂缓引入与触发条件

服务注册中心在出现动态地址、多实例扩缩容、实例自动替换、Compose 服务名无法满足寻址，且部署平台没有原生服务发现时进入正式评估。第一阶段闭环稳定后可以做限时学习实验，实验结果不自动改变主流程。进入 Kubernetes 后优先使用 Kubernetes Service。

配置中心在至少多个服务和多个环境之间出现大量共享普通配置、配置漂移、集中审计、版本回滚或动态刷新需求时进入评估。密码和密钥继续使用 Secret 管理。进入 Kubernetes 后优先使用 ConfigMap 和 Secret。

Keycloak、RocketMQ、Kafka、Kubernetes、Service Mesh、Seata、Distroless 和完整链路追踪平台暂不进入首期主流程。Redis、数据库迁移和持久化方案由「05-持久化与技术基线」决定。

## 验证清单

- 每个服务可以使用 IDE 或 Maven Wrapper 独立启动。
- 默认 Compose 可以启动基础依赖，并通过健康检查确认状态。
- 全链路 Compose Profile 可以启动 Gateway、IAM 和领域服务。
- React 可以通过 Authorization Code + PKCE 完成登录，API 使用 Access Token。
- Gateway 和领域服务都会拒绝签名、签发者、受众或有效期不正确的 Token。
- 领域服务直接访问时仍执行自己的 Token 和资源权限校验。
- 服务间 Client Credentials 调用可以区分调用服务身份和最终用户身份。
- 容器以非 root 用户运行，私钥没有进入镜像和 Git 仓库。
- 后续引入注册中心、配置中心或其他基础设施时，必须先满足本记录中的触发条件并新增决策记录。
